2.2 Governance principles

In short
  • The governance sets eight principles in three groups: compliant (GDPR-compliant, secure, EHDS-proof), flexible and scalable (continuous improvement, implementation freedom, scalable), and homogeneous data that remains federated (virtual cohort, federated).
  • Each principle limits the design. For example, Users never download personal data, analyses run in secure processing environments, as a rule in the countries, and no Member Country has to use one specific product.
  • Where principles pull in different directions, common interfaces and minimum requirements keep the system the same for Users, while each Member Country chooses how to implement them.

The principles at a glance​

The 1+MG Data Governance names eight principles, in three groups DG II.2. The governance derives them from the 1+MG Declaration, which the countries of the 1+ Million Genomes initiative signed, and adds principles that let the system grow to large amounts of data and many Users. This page treats them as constraints on the Genome EDIC system: every design must respect them.

The table says what each principle requires from the design, and which designs it rules out. The sections below give the design rules, each with the governance section it comes from.

Compliant​

GDPR-compliant​

The infrastructure should comply with the General Data Protection Regulation (GDPR) by design, follow recognised ethical standards, and make it easy for data subjects to exercise their rights DG II.2. The GDPR itself requires data protection by design and by default (Art. 25) [GDPR].

  • Data protection by design and by default in every component. The Genome EDIC Assembly of Members adopts the technical and organisational measures that all actors apply DG VI.1.1. The Genome EDIC CC drives tools built this way DG V.1.2. See 8.1.
  • A controller for every processing step. Each phase of the data lifecycle has its own controller or controllers, each with its own legal basis DG II.1. See 8.2.
  • As little data as possible, for as short a time as possible. The 1+MG Data Host releases only the data that the data use agreement covers DG VIII.3.3. Users confirm each year that they still need access, and can pause it for a sleeping period DG VIII.3.1.
  • Tools for data subjects' rights. Each Member Country provides the means to inform data subjects and to let them exercise their rights, ideally through a national portal DG V.2.4. The Genome EDIC CC provides the interfaces between the central information database (what data subjects can learn about the use of their data) and the national portals DG V.2.2. When a data subject exercises a right, the dataset gets a new version. A User who can't switch to the new version may keep using the one disclosed to them, and versioning keeps track of this DG V.2.6. The Assembly of Members sets the policy on such limits to data subjects' rights DG V.2.1. See 5.2.4 and 8.9.
  • Support for the data protection impact assessment (DPIA). 1+MG IT infrastructure providers support the controllers in performing it DG V.1.3.

Secure​

The IT infrastructure and processes in every Member Country must be vetted for security, so that together they form one coherent federation DG II.2.

  • Common security rules. The Assembly of Members adopts the security policies and an information security management system (ISMS) DG V.1.1. The Genome EDIC CC turns them into minimum requirements for audit and certification, and the Genome EDIC national entities implement them DG V.1.2.
  • Every node is audited or certified. Each 1+MG IT infrastructure provider (each node of the federation) is, at minimum, audited by an external body against the minimum requirements of the Genome EDIC CC, or works towards a certification such as ISO 27001, the international standard for information security management. Certification is mandatory for an SPE that pools data from other Member Countries DG V.1.3. Trust between the nodes rests on these checks. How providers are accredited is still to be defined DG III.
  • Measures that match the high risk: secure storage and processing, reliable authentication of each person and of their status (for example as an employee of a User Organisation), access logging, and encryption DG V.1.3. See 8.3, 8.4 and 8.5.
  • Revoke at once, and warn the others. When an SPE provider (a 1+MG IT infrastructure provider that runs an SPE) suspects a breach of purpose limitation or confidentiality, it revokes the User's access at once. It informs the Genome EDIC CC and the other affected SPE providers, ideally automatically DG VIII.3.3.

EHDS-proof​

The system should fit seamlessly into the EHDS, and add what the EHDS alone can't do DG II.2 [EHDS].

  • Metadata that fit the EU dataset catalogue. The ELSI metadata models must allow integration into the EHDS data catalogue, and may go beyond it DG VI.1.1. See 8.10.
  • An access request form that fits the EHDS form. The form of the 1+MG User Portal must integrate into the central EHDS data access request form, and may ask for more DG VII.3.1.
  • SPEs that meet the EHDS rules. SPEs should be compatible with the EHDS requirements for authorised participants (see 2.1) DG VIII.3.3. They can then also serve health data access bodies (HDABs) DG VIII.3.2.
  • Policies that follow the EHDS implementing acts. The policies of the Assembly of Members must be compatible with the implementing acts under Art. 75 EHDS DG V.1.1, among them the draft HealthData@EU implementing act [HDEU-IA draft]. See 8.11 and 5.1.5.
  • A data use agreement, not a data permit. The Genome EDIC can't issue EHDS data permits. It grants access through a data use agreement, together with a data processing agreement DG VIII.3.2. See 6.3.1.
  • Stricter than the EHDS where 1+MG needs it. According to the governance, the 1+MG rules may go further than the EHDS. The 1+MG rules prefer federation to pooling data in an SPE provided by the European Commission. They also ask for external audit or certification, where the EHDS asks only for an audit DG V.1.3.

Flexible and scalable​

Continuous improvement​

Member Countries keep defining the scope, conditions, minimum requirements and workflows together DG II.2. The governance sets principles. Working groups and committees turn them into implementation rules and technical requirements: for example, 1+MG Working Group 3 defines the data and metadata models DG II.1. The Assembly of Members decides on the principles, adopts the rules and sets the minimum requirements for harmonisation DG I. The Genome EDIC CC turns the security and risk policies into minimum requirements for audit and certification DG V.1.2.

  • Rules and models are versioned inputs. Data models, metadata models, access request forms and minimum requirements will change. Components treat them as versioned configuration, not as code, and say which version they follow. This is how the architecture applies the principle; the governance doesn't prescribe it.
  • One source of truth for information about the system. The Genome EDIC CC is the single source of truth for all relevant information across the federated system, such as its documentation DG V.1.2. The data themselves stay federated.
  • This architecture follows the governance. It is written against version 2025-12 of the governance [DG]. When the governance changes, the traceability page shows which pages to review.

Implementation freedom​

Member Countries choose how they fit the infrastructure into their national infrastructure, as long as they meet the requirements and implement the common functions DG II.2. The governance gives national implementation as much flexibility as possible, while the system stays homogeneous for the User DG I.

  • Interfaces first. Each component is described by its function, interfaces and standards. The GDI Starter Kit is named as the reference implementation [GDI Starter Kit]. A Member Country may use other tools that meet the same interfaces. See 4. Solution strategy.
  • Each country distributes the national roles. One organisation can hold several roles DG III, and countries should be as free as possible in how they share tasks DG VIII.3.3. Each Member Country records its choices in its national implementation profile. See 3.3.
  • Some choices are national by design. For example, whether data may be pooled for research DG VIII.3.4 (who decides this for 1+MG compliant datasets is still open, see below), or who reviews access requests for 1+MG cohort datasets DG VII.4.7. The system must support every option the governance allows, and show Users which one applies.
  • Common minimum requirements, checked by audit or certification. The freedom ends where the common requirements start. All SPEs meet the same minimum requirements DG VIII.3.3, and national entities are audited or certified against them DG V.1.2.

Scalable​

Implementations and procedures should scale to large data volumes and many Users DG II.2.

  • Do centrally what every country would otherwise repeat. The Genome EDIC CC takes on tasks that are more efficient at central level DG I, such as running the central data catalogue and managing access requests.
  • One access request for all data. One request covers all data available in the Genome EDIC, with a form per type of use, and the portal catches obvious mistakes before submission DG VII.3.1.
  • Machine-readable descriptions. ELSI metadata are harmonised and machine-readable DG VI.1.1, so that discovery and checks can be automated.
  • Compute and storage that scale. SPEs should plan for high-performance computing DG VIII.3.3. Archiving should avoid keeping several copies of datasets derived from the same data DG VIII.8.2. During a sleeping period, data can move to cold storage, which is cheaper but slower to access DG VIII.3.1.

Homogeneous data that remains federated​

Virtual cohort​

The data should behave, as much as possible, as one single cohort DG II.2.

  • Common data models. 1+MG Working Group 3 defines the data models, ontologies (shared vocabularies) and metadata models DG II.1. The Assembly of Members adopts them, with quality labels DG VI.1.1. 1+MG Data Providers transform their data into these models DG VI.2.2. The 1+MG NCP checks that they do, before the data are made available DG VI.4.4. See 5.2.6 and 8.10.
  • One catalogue, one portal, one procedure. Users find all data in one central data catalogue DG VII.2.1 and start from the 1+MG User Portal, whatever the country or the type of dataset. For 1+MG data they apply there; for externally governed datasets the portal sends them to the dataset's own procedure DG VII.3.1.
  • Analysis across countries. SPEs should allow efficient analysis of data from several 1+MG Data Providers and Member Countries, ideally federated across the national SPEs DG VIII.3.3.

Federated​

Personal data are held in a federated IT infrastructure. Users can only download non-personal results of analysis or aggregation DG II.2. As a rule, the data remain in the countries DG I.

  • Analysis runs in a 1+MG SPE. No download is possible, so each Member Country provides SPEs, and they all meet the same minimum requirements DG VIII.3.3. See 5.2.3 and 6.3.2.
  • Only non-personal results reach the User. Users must not export personal data DG VIII.2.2. See 8.8 Output control.
  • Pooling is an exception, chosen nationally. For research, the governance lets each Member Country keep its data federated only. It may instead allow "data streaming" (which the governance doesn't define further) or temporary pooling with data from other countries, where the purpose of the research can't be achieved otherwise. The choice is recorded as ELSI metadata in the dataset descriptions DG VIII.3.4. An SPE that pools data from other Member Countries must be certified DG V.1.3. The governance describes this choice for research only. Who takes it for 1+MG compliant datasets is still open (see below).
  • Own data and tools come in. Users may bring their own data and software into the SPE, after a security review. This includes data from HDABs and externally governed datasets DG VIII.3.1.
  • Reproducibility without download. As Users can't download personal data, the data must stay available through the Genome EDIC and its national entities, so that analyses can be run again DG VIII.8.1 DG VIII.8.2. See 6.3.7.

Where principles pull in different directions​

Some principles limit each other. The architecture handles them as follows.

  • Implementation freedom and virtual cohort. Countries choose their own tools, yet Users should see one system. Common interfaces, data models and minimum requirements keep the system the same for Users. What sits behind them is national DG I.
  • Federated, and analyses that need pooled data. Some analyses can't be done in a federated way. For research, the governance allows temporary pooling in a certified SPE, where the national choice allows it DG VIII.3.4. The system supports both, and shows Users which one applies to each dataset. Who decides for 1+MG compliant datasets is still open.
  • EHDS-proof, and stricter 1+MG rules. Components meet the EHDS interfaces and the stricter 1+MG requirements at the same time DG V.1.3. Some EHDS requirements are still a draft (see below).
Open points
  • Who decides on pooling for 1+MG compliant datasets. The recommendation lets each Member Country choose. Its justification says that for 1+MG compliant datasets the decision now rests with each 1+MG Data Holder, and that it could be taken at country level instead, to reduce complexity DG VIII.3.4. See chapter 11.
  • How 1+MG IT infrastructure providers are accredited is still to be defined DG III. See chapter 11.
  • The data and metadata models are not part of the governance: 1+MG Working Group 3 defines them, and the Assembly of Members adopts them DG II.1 DG VI.1.1. See chapter 11.
  • The HealthData@EU implementing act is still a draft [HDEU-IA draft], so the EHDS requirements for connection and for SPEs may still change. See chapter 11.
