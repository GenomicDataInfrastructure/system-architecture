1.1 Requirements overview

In short
  • This page lists the essential requirements on the system, in a short "shall" form, grouped by phase of the data lifecycle: bringing data in (inclusion), finding and requesting them (access), and analysing them (use), plus the requirements of the European Health Data Space.
  • The full requirements are in the 1+MG Data Governance and the EHDS. Each row points to the section it comes from, and to the page that describes it in detail.
  • Duties of organisations stay in the governance; this page says what the system must do to support them.

How to read this page​

The requirements come from the 1+MG Data Governance [DG] and the European Health Data Space (EHDS) [EHDS]. This page lists the ones that shape the architecture. Where a row reads differently from the section it cites, the section prevails, and the difference is a defect to report.

Each row is one requirement on the system:

  • shall: mandatory;
  • should: recommended, used only where the governance itself says "should";
  • may: optional.

Each row has an identifier, so that other pages can refer to it. The column Type of use follows the governance, which marks rules that apply only to some types of use. Deadlines and other thresholds are left to chapter 10, as quality scenarios. The lifecycle scenarios of chapter 6 give the steps; many of them are still being written.

The most important requirements​

The system serves the goals described in chapter 1. Five requirements matter most, because the rest depend on them:

  1. One catalogue for all datasets, and one access request for all 1+MG data, whatever the country or the type of dataset; externally governed datasets are listed, but follow their own access procedure (REQ-AC-2, REQ-AC-4).
  2. Analysis only in a secure processing environment (SPE), with no download of personal data (REQ-US-1).
  3. Access only for the four types of use DG II.3, each with its own request form (REQ-AC-4).
  4. The access decision follows the type of dataset: the system routes each request to those who decide on each dataset, and records the decision (REQ-IN-2, REQ-AC-5, REQ-AC-7a).
  5. Common data and metadata models, so that data from many countries can be found and analysed together (REQ-IN-1).

For healthcare reuse, there is no formal access decision per request: access rests on the framework data use agreement of the User Organisation DG VII.1.3 DG VII.5.4. The request is still checked by two people DG VII.4.3, the User Portal offers a staged request that asks for more detailed information step by step DG VII.3.1, and the system must be able to check in real time that the User is a licensed healthcare professional, or staff under medical secrecy, authorised under that agreement DG VII.1.3 DG VII.1.4 (chapter 11). 6.3.3 will describe the fast track.

Open points
  • Who informs data subjects after an access decision: the 1+MG NCP, or another national body. See chapter 11.
  • Who signs the data use agreement for 1+MG compliant datasets. See chapter 11.
  • Whether healthcare reuse and recruitment into clinical trials need new consent, or a new chance to object. See chapter 11.
  • How the status of a licensed healthcare professional is checked. See chapter 11.

What the system need not do​

The system gives access only for the four types of use, and offers no route for screening the data for secondary findings DG II.4. Chapter 1 explains what else the governance leaves out, and what the system still does for it. Until the Genome EDIC is operational, the system gives access only to externally governed datasets (ADR-0003, proposed; chapter 11); chapter 1 lists what the GDI project already delivers.

Retired IDs, never reused: REQ-IN-4 (merged into REQ-AC-2); REQ-IN-6 (data stay with 1+MG Data Hosts: 2.2, 5.2.5); REQ-AC-6 (healthcare reuse fast track: 6.3.3); REQ-US-2 (the Genome EDIC as processor: 8.2); REQ-US-4 (yearly reconfirmation and sleeping period: 6.3.2, 8.1); REQ-US-6 (questions to the treating healthcare professional: 6.3.3); REQ-US-7 (archiving: 6.3.7); REQ-US-8 (merged into REQ-AC-8); REQ-US-9 (incidental findings: 6.3.8); REQ-US-10 (intellectual property: 6.3.6); REQ-US-12 (recruitment of data subjects: 6.3.5); REQ-EH-4 (SPEs that serve health data access bodies: 8.11, 5.2.3). REQ-AC-7, REQ-US-3 and REQ-US-5 were split into a and b.
