1.2 Quality goals

In short
  • Four quality goals matter most for the architecture, in this order: data protection, security and data subjects' rights; one system for the User; freedom for each country to implement its part; and growth to many Users and much data.
  • Each goal comes from the governance principles. Where goals pull in different directions, the protection of data subjects comes first.
  • Chapter 10 will make each goal measurable with test scenarios. Until then, this page says how we will know a goal is met.

The quality goals​

The governance names eight principles DG II.2, described in 2.2 Governance principles. The four quality goals below group them, categorised according to the ISO/IEC 25010 quality model [arc42] [ISO/IEC 25010:2023]; those terms are in the last line of each cell.

Each goal has an identifier, QG-1 to QG-4, which also gives its priority: QG-1 comes first. The priority decides which goal wins when two conflict. Chapter 4 and chapter 10 refer to the goals by these identifiers.

IDQuality goalWhat it meansMotivation (governance principle)Where it is addressed
QG-1Data protection, security and data subjects' rights
ISO/IEC 25010: security (confidentiality, integrity, accountability, authenticity)		Users process personal data only for an approved purpose, in a secure processing environment (SPE), and can't download them. Every other actor processes only the personal data its task needs, as the controller or processor named in 8.2. Every access to personal data, including each subject-level search, is logged and traceable to a person and a User Organisation. Every node of the federation (each organisation that runs a part of the system) is audited by an external body against the same minimum requirements, and/or works towards certification. Data subjects are informed about each project; their consent preferences and objections decide which records a User can find and receive; and they can exercise their rights through a national portal.GDPR-compliant, secure, federated DG II.2. Technical and organisational measures that reflect the high risk DG V.1.3, under a common risk management framework and information security management system (ISMS) DG V.1.1. Tools for data subjects' rights DG V.2.4; information after each access decision DG VII.5.3.4, 8.1, 8.3, 8.4 (ADR-0004 and ADR-0006, wave 3), 8.5, 8.8, 6.4, 6.5
QG-2One system for the User
ISO/IEC 25010: compatibility (interoperability); interaction capability		A User finds all data in one catalogue, applies once through one procedure, and analyses data from several countries as if they were one cohort. The system fits the European Health Data Space (EHDS): its metadata, request form and SPEs can connect to HealthData@EU.Virtual cohort, EHDS-proof, scalable DG II.2. "Homogeneity towards the user" is the guiding principle DG I. Common data models DG VI.1.1, one access request DG VII.3.1.4, 8.10 (ADR-0007, wave 3), 8.11 (ADR-0008, wave 3), 5.1.1
QG-3Freedom to implement, and to change
ISO/IEC 25010: flexibility (adaptability, replaceability); maintainability (modifiability)		Each Genome EDIC Member Country can use its own tools and organisations, as long as they meet the common interfaces and minimum requirements. Data models, request forms and minimum requirements can change without rebuilding the components.Implementation freedom, continuous improvement DG II.2.4, national implementation profile
QG-4Growth
ISO/IEC 25010: flexibility (scalability); performance efficiency (capacity)		The system keeps working as countries, datasets, Users and requests are added. Analyses across countries run efficiently, with high-performance computing where needed.Scalable DG II.2. SPEs that allow efficient analysis across countries DG VIII.3.3.4, 5.2.3, chapter 7

The goals are architecture goals, not project goals. How many genomes are made available, or by when, is not a quality goal.

Open point

How 1+MG IT infrastructure providers are accredited, and how accreditation relates to audit and certification, is still to be defined. See chapter 11.

When goals conflict​

  • Data protection before convenience. Where one system for the User would mean pooling data or showing more detail in a search, data protection wins. Data stay federated as a rule DG II.2, and pooling is a national exception for research only DG VIII.3.4. The governance gives the protection of data subjects the highest priority: if in doubt, no data are disclosed DG VII.5.1. See 2.2.
  • One system for the User before national variety. Countries are free in how they implement, but not in the interfaces the User sees DG I. For example, every country's catalogue entries follow the same metadata model, while each country chooses which software runs its catalogue.
  • Freedom before growth. A faster central shortcut that takes away a national choice is not taken. Growth comes from doing centrally what every country would otherwise repeat, such as the User Organisation registry, behind common interfaces.

How we will know a goal is met​

Chapter 10 will turn each goal into quality scenarios with a measurable response, numbered QS-1, QS-2 and so on, each naming the goal it tests. It is written in a later wave, and will set the targets. Until then, these are the indicators:

Quality goalHow we will knowInputs
QG-1 Data protection, security and data subjects' rightsEvery release of results from an SPE passed output control and is logged with its reviewer. Every SPE session and every subject-level search is traceable to a person and a User Organisation DG VII.2.3. Every node holds a current audit report against the minimum requirements of the Genome EDIC CC, or works towards certification DG V.1.3. A 1+MG Data Host releases only what the data use agreement covers. Data subjects are informed of each approved project within 1 working day, for the types of use that VII.5.3 covers. Tests show that a record whose data subject objected, or didn't consent, is neither counted in discovery nor released. A change that follows a data subject's request reaches a new dataset version and the Users concerned.Acceptance criteria for central and local nodes [B1MG+ D2.10]; the risk management framework that B1MG+ proposes for the Genome EDIC [B1MG+ D2.9], until the Genome EDIC Assembly of Members adopts one DG V.1.1
QG-2 One system for the UserA User can find, request and analyse data from several countries without country-specific steps. Catalogue entries validate against the common metadata models. The register of access requests and approvals is published and complete DG VII.5.5.Data quality and distributed analysis requirements [GDI D6.3]
QG-3 Freedom to implement, and to changeA Member Country can replace a reference component with another tool that passes the same interface tests. A new version of a data model can be rolled out without rebuilding the components.Indicators for software and metadata quality [B1MG+ M4.6]
QG-4 GrowthQuality of service metrics, reported for each node, stay within agreed limits as nodes and Users are added.Quality of service metrics and technology readiness levels (TRLs) of the nodes [GDI D5.5]

Four other qualities matter, but are not top goals of the architecture:

  • Data quality. The clinical and phenotypic data must be of high quality, above all for quality management in healthcare, where they inform treatment recommendations DG II.3. The Genome EDIC Assembly of Members adopts quality labels with the data models DG VI.1.1. See 8.10.
  • Software quality and maturity. The GDI project measures the maturity of each node with technology readiness levels [GDI D5.5], and B1MG+ proposes indicators for software and metadata quality [B1MG+ M4.6].
  • Availability and business continuity. Each node plans for backup, recovery and continuity under the risk framework DG V.1.1; nodes in scope of the NIS2 Directive must do so under national law (2.1).
  • Non-functional requirements of the GDI products. The GDI project has its own non-functional requirements for its products. Chapter 10 will take over those that the architecture needs.
