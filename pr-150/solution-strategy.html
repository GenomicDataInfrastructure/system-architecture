4. Solution strategy

In short
  • The data stay in the countries as a rule. Users analyse personal data only in secure processing environments, and can download only non-personal results. Users still see one system, with one portal, one catalogue and one access request.
  • Common interfaces, data models and minimum requirements hold the federation together; behind them, each country chooses its own tools and organisations. The GDI Starter Kit (ready-made software from the GDI project that countries may use or replace) and the GDI central services are the reference implementation, not a requirement.
  • Data subjects are informed through national portals, and Users never contact them. Responsibility follows the data lifecycle and the type of dataset, not the location of servers. The system is built in steps, and designed from the start to connect to the European Health Data Space.

The fundamental choices​

In one sentence: the data stay where they are and are analysed where they are, while one central entry point and common rules make the system look like one to its Users and transparent to data subjects.

Each row links an approach to the quality goals of 1.2 (QG-1 to QG-4) or the constraint it serves. The design rules that follow from each governance principle are in 2.2 Governance principles; this page gives the strategy and its reasons, and links to them.

The candidate decisions listed in chapter 9 (federated processing, no download, key-coded identifiers, interfaces first) are stated here first. Each is to become an architecture decision record (ADR); until then, this page and the governance give their reasons.

Federation: the data stay where they are​

Personal data stay in the countries, held by 1+MG Data Hosts in 1+MG compliant local IT infrastructure (the hosts' IT that meets the 1+MG requirements, not to be confused with 1+MG compliant datasets), and are analysed in 1+MG SPEs. The rules are in 2.2 Federated.

Why: the governance calls federation itself "a protective measure" DG VIII.3.4. It keeps each country in control of its data, and keeps copies few. It also lets the system grow: a new country or dataset joins as a node behind the same interfaces, without moving data. The EHDS states the same idea in its recitals: bringing questions to data instead of moving those data, whenever possible (recital 80) [EHDS]. Its operative rules don't require federated computing; they rely on secure processing environments, and allow pooling in the Commission's SPE. The governance chooses federation where it can DG VIII.3.3.

What we gave up: a permanent central copy of all data, which would make analysis across countries simpler. Instead, SPEs should allow efficient analysis across countries, ideally federated across the national SPEs, with high-performance computing where needed DG VIII.3.3. For research, a Member Country may allow temporary pooling in a certified SPE, where the purpose can't be achieved in a federated way, or would be too complicated to implement that way DG VIII.3.4 DG V.1.3.

Open points
  • Who decides on pooling for 1+MG compliant datasets. See chapter 11.
  • When 1+MG data may be processed in the SPE of the European Commission. See chapter 11.

No download of personal data​

Users analyse personal data only in a 1+MG SPE, or where applicable in the SPE of the European Commission, and can download only non-personal results DG II.2 DG VIII.2.2. Data and software that Users bring into an SPE pass a security review by the 1+MG IT infrastructure provider first DG VIII.3.1 (5.2.3).

The governance provides for a few other exits, each controlled and logged: reports of incidental findings to the entity mandated nationally DG VIII.11.2, temporary pooling in a certified SPE DG VIII.3.4, and, where applicable, the SPE of the European Commission DG VIII.2.2 (3.1).

Why: it is the strongest single safeguard against misuse and re-identification, and it lets one set of SPE controls protect every dataset.

A consequence for the roles: because all analysis happens in SPEs that the Genome EDIC sets the rules for, the Genome EDIC can act as processor for the User Organisation, under one data processing agreement, with the SPE providers as sub-processors DG VIII.2.1. The governance chose this so that the User Organisation doesn't carry the responsibility for the federated SPE system DG VIII.2.1.

Open point

Whether SPE providers are only sub-processors, or also controllers for their own platform processing; ADR-0010 proposes the split. See chapter 11.

Data protection by design and by default​

Every component starts from the least data and the narrowest access. The mechanisms for each GDPR principle are in 8.1. The main ones:

  • key-coded identifiers replace names and other direct identifiers; genomic data, which can identify a person by themselves, are stored apart from the clinical data DG VI.4.1;
  • subject-level data discovery returns counts, with safeguards built into the search engine DG VII.2.3;
  • the 1+MG Data Host releases only the data that the data use agreement covers DG VIII.3.3;
  • unnecessary copies are avoided DG VI.4.6;
  • access is reconfirmed each year and can be paused DG VIII.3.1.

Why: the GDPR requires it (Art. 25) [GDPR], and the governance asks the Genome EDIC CC to drive tools built this way DG V.1.2. The 1+MG requirements for IT infrastructure were themselves derived from a data protection by design and by default approach, with no access as the default [1+MG DPbDD IT requirements].

Data subjects informed through national portals​

Project information is captured once, in the User Portal, and passed to central and national information portals. There, data subjects are informed, set their preferences and exercise their rights DG V.2.4 DG VIII.1.2. The link between identity and key-coded identifier stays in the country (decided in ADR-0005 (wave 3), described in 8.7). Users never receive contact data: invitations to studies go through the national information chain DG VIII.5.1 DG VIII.5.3. A public register shows access requests and approvals DG VII.5.5.

Why: the governance makes compliance with data subjects' rights part of the principle GDPR-compliant DG II.2, and makes informing data subjects a national task DG V.2.4. Keeping the identity link and the contact in the country means no central service ever needs to know who a data subject is. See 5.1.4, 5.2.4, 6.3.4, 6.4 and 8.9.

One-stop shop for Users​

The Genome EDIC CC is the one-stop shop for Users, and does centrally what is more efficient there DG I. It runs the 1+MG User Portal and the central data catalogue DG VII.2.1, receives one access request for all data DG VII.3.1, and registers and vets User Organisations DG VII.1.2, on behalf of the 1+MG Data Holders for 1+MG compliant datasets DG VII.1.1. The national review and decisions sit behind it, reached through each 1+MG NCP.

Why: without it, a User would have to register, apply and wait in each country. Central tasks are done once, however many countries join. The GDI project compared central, partly decentralised and fully decentralised access request management, and dropped the fully decentralised option, because it doesn't give Users the harmonised interface the governance requires (GDI D3.4, section 4.4) [GDI D3.4]. Each country can still run a local tool behind the central one.

What we gave up: the central services become a point every country relies on. They hold no data about data subjects, but the integrity of their access decisions and registrations is critical: a 1+MG Data Host releases data on the basis of the data use agreement the Genome EDIC CC issues DG VIII.3.3 DG VII.5.5 (8.3).

Risk

A tampered or wrong central access decision or registration could lead national nodes to release data. See chapter 11.

Common models​

The Genome EDIC Assembly of Members adopts the data models, the metadata models and the ELSI metadata models for all countries DG VI.1.1. Every 1+MG Data Provider transforms its data into them before inclusion.

Why: a virtual cohort, where the data behave as one dataset, is only possible if every country describes and structures its data the same way DG II.2. Machine-readable ELSI metadata also let the system check automatically which uses each dataset and each data subject's consent allow, so that discovery and release include only records whose data subjects allow the stated use DG VI.1.5 DG VII.2.3.

Open point

The data and metadata models are defined outside this architecture. See chapter 11.

Interfaces first, with a reference implementation​

Each component is described first by its function, interfaces and standards: that is what Member Countries must meet to work together. Chapter 5 follows this for every building block. Its reference implementation is then named: the GDI Starter Kit component for national nodes, or the GDI central service for the European scope [GDI Starter Kit]. A Member Country may use other tools that meet the same interfaces.

Why: the governance gives each country freedom in how it fits the system into its national infrastructure DG II.2, and one organisation may hold several roles DG III. Specifying products would take that freedom away; specifying nothing would break the federation. The governance doesn't prescribe how components are specified; interfaces first is the architecture's way of applying the principle implementation freedom. HealthData@EU works the same way: national contact points and authorised participants must meet common requirements and technical specifications (EHDS Art. 75(6); the draft implementing act under Art. 75(12) [HDEU-IA draft]), and TEHDAS2 recommends that any conforming solution may be deployed [TEHDAS2 D7.3].

Trust through common minimum requirements​

Every node of the federation meets the same minimum requirements, set by the Genome EDIC CC. Each 1+MG IT infrastructure provider is audited by an external body against them, and/or works towards certification; an SPE that pools data from other Member Countries must be certified DG V.1.2 DG V.1.3.

Why: the nodes are run by different organisations in different countries. Users, 1+MG Data Holders and other nodes can only rely on a node they don't run if it is checked against the same rules. Audit doesn't replace checks at run time: every crossing of a trust boundary between nodes run by different organisations is still authenticated and encrypted (3.1; decided in ADR-0006 (wave 3), described in 8.3).

What GDI already delivers: a compliance framework for its nodes, with common standard operating procedures and a Security and Data Protection Committee. The first compliance assessment was postponed until the nodes are operational [GDI MS13].

Open point

How 1+MG IT infrastructure providers are accredited is still to be defined. See chapter 11.

Versioned rules and models​

Data models, metadata models, access request forms and minimum requirements will change. Components treat them as inputs with a version, so that they can be updated without rebuilding the software, and each part of the system says which version it follows. Datasets are versioned too, so that each User knows which version they work with (8.9).

Why: the governance expects Member Countries to keep defining the scope, conditions and requirements together DG II.2, and leaves the technical requirements to committees and working groups DG II.1. A design that builds one version in would have to be rebuilt each time. The governance doesn't prescribe how to follow its changes; this is the architecture's way of applying the principle continuous improvement.

Responsibility follows the lifecycle and the type of dataset​

The three scopes (European, national and User Organisation) are scopes of responsibility, not places where servers run. Each phase of the lifecycle has its own controller or controllers, with its own legal basis DG II.1. The type of each dataset decides who takes the access decision: a 1+MG Data Holder in the country, or the Genome EDIC. The system supports all three types of dataset, and each Member Country chooses between the two 1+MG types for its datasets (ADR-0002, proposed); the level of the choice is still open (chapter 11).

Why: responsibility in the Genome EDIC doesn't follow the system boundary. For 1+MG cohort datasets, for example, the Genome EDIC decides on access, but the data stay with a 1+MG Data Host in the country. Designing by responsibility makes every processing step traceable to a controller (8.2).

Open point

Whether the Genome EDIC is joint controller with the 1+MG Data Holder for 1+MG compliant datasets; ADR-0009 proposes that it is. See chapter 11.

Build in steps​

The system starts with externally governed datasets, and adds 1+MG compliant and then 1+MG cohort datasets once the Genome EDIC is operational (2.1). Every catalogue entry states its type from the first step, so that each step adds a way to access data without changing what Users do (ADR-0003, proposed).

In the first step, the datasets follow their own governance, not the 1+MG Data Governance. The catalogue labels them as external DG VII.2.1, and the 1+MG safeguards for purposes and for informing data subjects apply from the second step. Chapter 1 lists what the GDI project already delivers.

Why: the Genome EDIC can't be assumed to be operational before GDI ends, in March 2027 [GDI D4.4]. Building in steps delivers access to some data now, and keeps the later steps compatible.

Open points
  • Until the Genome EDIC is operational, who runs the central services, and who is controller and processor for them, is not decided. See chapter 11.
  • Who sets and checks the quality and ELSI inclusion criteria for externally governed datasets. See chapter 11.
Risk

GDI may end before the Genome EDIC is operational. See chapter 11.

Fit with the EHDS​

The system is designed so that the Genome EDIC can become an authorised participant in HealthData@EU (EHDS Art. 75(4)) [EHDS]: its metadata can be integrated into the EU dataset catalogue DG VI.1.1, its access request form integrates into the EHDS form DG VII.3.1, and its SPEs should meet the EHDS requirements, so that they can also serve health data access bodies DG VIII.3.3. The HealthData@EU requirements apply to the Genome EDIC only once it is an authorised participant. The Commission connects an authorised participant by implementing decision (Art. 75(13)), under the conditions and compliance checks of the implementing act under Art. 75(12)(b), still a draft [HDEU-IA draft]. Separately, the EHDS applies to 1+MG Data Providers and 1+MG Data Holders that are health data holders in any case, from 26 March 2029 (genomic data from 26 March 2031).

The Genome EDIC is not a health data access body. It issues data use agreements, not data permits, and its rules can be stricter than the EHDS where 1+MG needs it (2.1).

Why: fitting the EHDS from the start avoids building formats and interfaces that only work inside 1+MG DG II.2. Waiting for the final EHDS rules before designing would leave the system without an architecture until 2029.

Open point

The HealthData@EU implementing act is still a draft. See chapter 11.
