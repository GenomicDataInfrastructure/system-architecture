# Documentation decisions and open questions

Log decisions about how we write and organise the architecture documentation (not architecture decisions about the system; those go in chapter 9 as ADRs).

Format: `D-NNN | date | decision | decided by | reason`

## Decisions
- D-001 | 2026-09-18 | Use the arc42 template | Taskforce (B. Pacheco) | Requested template; well known to implementers.
- D-002 | 2026-09-18 | Publish with Docusaurus on GitHub Pages | Taskforce (B. Pacheco) | Static site, versioned, reviewable through pull requests.
- D-003 | 2026-09-18 | Track authorship and review in GitHub: page front matter, CODEOWNERS, branch protection, PR template, Project board, tagged releases | Proposed, to confirm | No extra tool; approvals are timestamped and attributable.
- D-004 | 2026-09-18 | Keep planning context in `planning/` and `AGENTS.md` in the repository | B. Pacheco | Context must survive across chat sessions and new taskforce members; `AGENTS.md` keeps the repository AI-tool agnostic.
- D-005 | 2026-09-18 | Structure: one top-level arc42; chapters 5 and 7 split into European, national and local scopes; each Member Country fills in a national implementation profile | B. Pacheco | Answers Q-001. Easiest to read and keep consistent; respects implementation freedom. **Scopes replaced by D-018.**
- D-006 | 2026-09-18 | Describe the Genome EDIC target state for all four uses (research, policy development, QM in healthcare, healthcare reuse); flag what the GDI MVP already delivers | B. Pacheco | Answers Q-002.
- D-007 | 2026-09-18 | Components are technology-neutral (functions, interfaces, standards), mapped to the GDI Starter Kit as reference implementation | B. Pacheco | Answers Q-007. Keeps national implementation freedom. **Refined by D-020.**
- D-008 | 2026-09-18 | Cite the draft HealthData@EU implementing regulation openly, labelled as a Commission draft | B. Pacheco | Answers Q-004. Its text is not copied into the repository.
- D-009 | 2026-09-18 | Traceability is generated: pages list governance section IDs in `governance_refs`; the site builds the traceability matrix and document status page from front matter; `npm run check` validates it in CI | B. Pacheco (Phase 0) | One source of truth; no hand-maintained matrix.
- D-010 | 2026-09-18 | Publish in the public repository GenomicDataInfrastructure/system-architecture (GitHub Pages: genomicdatainfrastructure.github.io/system-architecture); keep the GDI OSS template's REUSE licensing (docs CC-BY-4.0, code Apache-2.0) and code of conduct; drop its Docker files and workflows | B. Pacheco | Answers Q-005. Follows GDI open-source practice.
- D-011 | 2026-09-18 | Track roles and responsibilities only with GitHub issues (one per page; assignee = owner; reviewers named in the issue and requested on the pull request) and the page front matter (`owner`, `reviewers`, `status`, `last_reviewed`). No CODEOWNERS, review teams or Project board for now; `main` requires one approval and passing CI | B. Pacheco | Replaces the CODEOWNERS and Project board parts of D-003; simpler for a small taskforce. Can be revisited when the taskforce grows.
- D-012 | 2026-09-18 | The governance master document (2025-12-22, "for voting") is not public but may be cited: section numbers (`<GovRef>`), short summaries in our own words, and short attributed quotes. No long passages. The glossary keeps the governance definitions (section III) word for word, as short attributed quotes | B. Pacheco | Answers Q-003. **Superseded by D-016.**
- D-013 | 2026-09-18 | Taskforce authors are comfortable with Git and GitHub: everyone works with branches and pull requests; no extra editing tool | B. Pacheco | Answers Q-006.
- D-014 | 2026-09-18 | No global list of priority sources: each chapter owner chooses sources when the chapter starts, and candidates are searched then | B. Pacheco | Answers Q-008.
- D-015 | 2026-09-18 | Pages are written in six waves (Frame; Direction and legal frame; Structure; Behaviour and components; Crosscutting details; Deployment, quality and consolidation), recorded in each page's `wave` field; a wave starts when the waves it depends on are at least in review. Authors follow the taskforce handbook (choreography, recipes, sources, review checklists) | B. Pacheco | Gives the taskforce a shared order and a repeatable way to write and review each page.
- D-016 | 2026-09-24 | The governance master document is published: version 2025-12, as the annex (section 7) of GDI D2.4 Framework for data governance, https://zenodo.org/records/19096953 (DOI 10.5281/zenodo.19096953, CC BY 4.0). Cite the document with `<Cite id="dg" />` and its sections by number with `<GovRef>`, never by page number. The section catalogue follows the published numbering. The overview section, printed as "I.", keeps the ID `IV` (its place between III and V). Its unnumbered topic headings are not catalogued. We still summarise in our own words and quote only definitions (word for word) and short passages, with attribution | B. Pacheco | Replaces D-012. Page numbers differ between versions and PDFs; section numbers don't.
- D-017 | 2026-09-24 | Cite the draft HealthData@EU implementing regulation (Ref. Ares(2026)8339104) through its public page on the Commission's Have your say portal, initiative 16155: https://ec.europa.eu/info/law/better-regulation/have-your-say/initiatives/16155-European-Health-Data-Space-technical-requirements-for-HealthData@EU_en. It stays labelled as a draft, and its text is still not copied into the repository | B. Pacheco | The draft was published for feedback on 2026-09-01; readers can open it themselves. Complements D-008.
- D-018 | 2026-09-24 | Scopes are scopes of responsibility: **European** (Genome EDIC: Genome EDIC CC, 1+MG DAC), **national** (everything a Genome EDIC Member Country is responsible for: 1+MG NCP, 1+MG Data Holders, 1+MG Data Providers, 1+MG Data Hosts, Local DACs) and **User Organisation** (the User Organisation and its Users). There is no separate local scope. Chapter 5 is split by scope; chapter 7 by the IT levels of the governance (central, national, local). The 1+MG IT infrastructure provider is a role that can appear in any scope. The "who decides on access" question per type of dataset is recorded as ADR-0002 | B. Pacheco | Replaces the scopes of D-005. Within a country, the Member Country decides which organisation takes which role, and one organisation can hold several roles, so a national/local boundary would differ per country. The User Organisation is the controller for the downstream use and starts several processes (registration, onboarding and offboarding of Users, access requests) (governance VII.1.3).
- D-019 | 2026-09-24 | Architecture diagrams are drawn in draw.io and saved as `.drawio.svg` in `static/diagrams/` (one file is both the editable source and the image), named after their section and shown with `<Diagram>`. The notation is chosen per diagram: C4 by default for structure (context, scopes, building blocks, deployment), UML sequence diagrams for runtime scenarios, another notation where it explains better; the legend names it. Every diagram has a white background (same look in light and dark mode) and a legend with its section and the date of its last edit, updated on every edit. Scopes keep the same colours everywhere. No shared template. `npm run diagrams` re-exports diagrams in light colours; `npm run check` checks the file, the legend date and the colours. Mermaid is no longer used in architecture pages; the handbook keeps a few simple flowcharts. Rules in the handbook page *Diagrams* | B. Pacheco | Mermaid gave no control over the layout and was hard to read in dark mode and on small screens. draw.io saves colours that change in dark mode by default, hence the re-export command and the check.
- D-020 | 2026-09-25 | **Interfaces first** (refines D-007). Each component is described first by its function, interfaces and standards: that is what Member Countries must meet to work together. Then its reference implementation is named openly: the GDI Starter Kit component for national nodes, or the GDI central service for the European scope, including components built only for GDI. A Member Country may use other tools that meet the same interfaces (governance II.2, implementation freedom). The central services have a single implementation, which the architecture documents as it is | B. Pacheco | "Technology-neutral, not products" was open to challenge: GDI ships a Starter Kit with specific tools, and some central components were built only for GDI. Naming them as reference implementation, behind the interfaces, is accurate and keeps implementation freedom.
- D-021 | 2026-09-25 | Acronyms: instead of expanding every acronym on every page, the first use of each acronym on a page links to the glossary with `<Term id="…" />`, which shows its meaning as a tooltip. The acronyms and their meanings live in one data file (`src/data/acronyms.json`), which also generates the glossary's acronym table; `npm run check` rejects unknown acronyms. Acronyms inside a governance term ("1+MG Data Holder", "Genome EDIC CC") are covered by the term's glossary entry | B. Pacheco | Readers often land on a page directly, so each page needs its own first link; repeating expansions on every page drifts over time, and one list keeps them consistent.
