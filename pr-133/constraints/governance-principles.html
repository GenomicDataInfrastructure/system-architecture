2.2 Governance principles

In short
  • The governance sets eight principles in three groups: compliant (GDPR-compliant, secure, EHDS-proof, that is, fitting the European Health Data Space), flexible and scalable (continuous improvement, implementation freedom, scalable), and homogeneous data that remains federated (virtual cohort, where the data look like one dataset to Users, and federated).
  • Each principle limits the design. For example, Users never download personal data, analyses run in secure processing environments, which as a rule are in the country where the data are, and no Member Country has to use one specific product.
  • Where principles pull in different directions, common interfaces and minimum requirements keep the system the same for Users, while each Member Country chooses how to implement them.

The principles at a glance​

The 1+MG Data Governance names eight principles, in three groups DG II.2. The governance derives them from the 1+MG Declaration, which the countries of the 1+ Million Genomes initiative signed, and adds principles that let the system grow to large amounts of data and many Users. This page treats them as constraints on the Genome EDIC system: every design must respect them.

The table says what each principle requires from the design, which designs it rules out, and where it comes from in the governance. The sections below give the design rules, each with the governance section it comes from.

Compliant​

GDPR-compliant​

The infrastructure should comply with the General Data Protection Regulation (GDPR) by design, follow recognised ethical standards, and make it easy for data subjects to exercise their rights DG II.2. The GDPR itself requires data protection by design and by default (Art. 25) [GDPR].

  • Data protection by design and by default in every component. The Genome EDIC Assembly of Members adopts the technical and organisational measures that all actors apply DG VI.1.1. The Genome EDIC CC drives tools built this way DG V.1.2. See 8.1.
  • A controller for every processing step. Each phase of the data lifecycle has its own controller or controllers, each with its own legal basis DG II.1. See 8.2.
  • Access only for the four types of use. The system gives access only for research, policy development, quality management in healthcare and healthcare reuse, each with its own request form and review DG II.3 DG VII.3.1. Screening the data for secondary findings, to find people who could benefit from a treatment, is outside the governance DG II.4.
  • Ethical review. The 1+MG DAC checks each request for ethical issues that affect data subjects. It can call on an additional review committee for vulnerabilities, with representatives of the affected groups DG VII.4.2. If in doubt, no data are disclosed DG VII.5.1.
  • As little data as possible, for as short a time as possible. The 1+MG Data Host releases only the data that the data use agreement covers DG VIII.3.3. Users confirm each year that they still need access, and can pause it for a sleeping period DG VIII.3.1.
  • Tools for data subjects' rights. Each Member Country provides the means to inform data subjects and to let them exercise their rights, ideally through a national portal DG V.2.4. The Genome EDIC CC provides the interfaces between the central information database (what data subjects can learn about the use of their data) and the national portals DG V.2.2. See 5.2.4.
  • Rights change the data, and Users follow the change. When a data subject exercises a right, the dataset gets a new version. By default, Users must accept that the data change. Only where a stable dataset is justified, and announced early through the User Portal, does a User keep the version disclosed to them DG V.2.7. Data subjects are told about such limits before they consent or object DG V.2.2. Versioning keeps track of which version each User uses DG V.2.6. The Assembly of Members adopts the policy on how rights are handled, including the limits the GDPR allows, for example where data can't be removed from a completed analysis DG V.2.1 [GDPR]. See 8.9.
  • Support for the data protection impact assessment (DPIA). 1+MG IT infrastructure providers support the controllers in performing it DG V.1.3.

Secure​

The IT infrastructure and processes in every Member Country must be vetted for security, so that together they form one coherent federation DG II.2. Each 1+MG IT infrastructure provider is a node of this federation. Some providers also fall under the NIS2 Directive: see 2.1.

  • Common security rules. The Assembly of Members adopts the security policies and ensures that an information security management system (ISMS) is implemented DG V.1.1. The Genome EDIC CC turns them into minimum requirements for audit and certification, and the Genome EDIC national entities implement them DG V.1.2.
  • Every node is audited, or works towards certification. Each 1+MG IT infrastructure provider is, at minimum, audited by an external body against the minimum requirements of the Genome EDIC CC, and/or works towards a certification such as ISO 27001 (the international standard for information security management) or NIST. Certification is mandatory for an SPE that pools data from other Member Countries DG V.1.3. Trust between the nodes rests on these checks. How providers are accredited is still to be defined DG III.
  • Measures that match the high risk: secure storage and processing, reliable authentication and authorisation of each person and of their status (for example as an employee of a User Organisation), access logging, encryption, and reduction of the identifiability of tabular data DG V.1.3. Identity and authorisation are decided in ADR-0004, and what each crossing between operators requires in ADR-0006 (both wave 3). See 8.3, 8.4, 8.5 and 8.7.
  • Revoke at once, and warn the others. When an SPE provider (a 1+MG IT infrastructure provider that runs an SPE) suspects a breach of purpose limitation or confidentiality, it revokes the User's access at once. It informs the Genome EDIC CC and the other affected SPE providers, ideally automatically DG VIII.3.3. The Genome EDIC CC then revokes the access legally, and may bar the User or the User Organisation from future access DG VIII.3.2. See 6.5.

EHDS-proof​

The system should fit seamlessly into the EHDS, and add what the EHDS alone can't do DG II.2 [EHDS].

  • Metadata that fit the EU dataset catalogue. The ELSI metadata models, which describe for each dataset the consent and the uses allowed, must allow integration into the EHDS data catalogue, and may go beyond it DG VI.1.1. See 8.10.
  • An access request form that fits the EHDS form. The form of the 1+MG User Portal must integrate into the central EHDS data access request form, and may ask for more DG VII.3.1.
  • SPEs that meet the EHDS rules. SPEs should be compatible with the EHDS requirements for SPEs and for authorised participants in HealthData@EU (EHDS Art. 73 and Art. 75(6); see 2.1) DG VIII.3.3. They can then also serve health data access bodies (HDABs) DG VIII.3.2.
  • Policies that consider the EHDS implementing acts. The Assembly of Members should consider the compatibility of its policies with the implementing acts under the EHDS DG V.1.1, among them the draft HealthData@EU implementing act (EHDS Art. 75(12)) [HDEU-IA draft] and the act on SPE requirements (EHDS Art. 73(5)). The Genome EDIC CC must consider the requirements for taking part in the EHDS DG V.1.2. See ADR-0008 and 8.11.
  • A data use agreement, not a data permit. The Genome EDIC is not a health data access body, and can't issue EHDS data permits (EHDS Art. 68) [EHDS]. Under the 1+MG data governance, the access decision is taken per type of dataset (8.12). Access then rests on a data use agreement, issued by the Genome EDIC CC DG VII.5.5, and a data processing agreement DG VIII.2.1. Who signs the data use agreement for 1+MG compliant datasets is still open (see below). See 6.3.1.
  • Stricter than the EHDS where 1+MG needs it. According to the governance, the 1+MG rules may go further than the EHDS. The 1+MG rules prefer federation to pooling data in the SPE provided by the European Commission under the EHDS. The EHDS asks for an audit of the SPE (EHDS Art. 73(3)); 1+MG asks for an audit by an external body, or a certification DG V.1.3.

Flexible and scalable​

Continuous improvement​

Member Countries keep defining the scope, conditions, minimum requirements and workflows together DG II.2. The governance sets principles. Working groups and committees turn them into implementation rules and technical requirements: for example, 1+MG Working Group 3 (Standards) defines the data and metadata models DG II.1. The Assembly of Members decides on the principles, adopts the rules and sets the minimum requirements for harmonisation DG I. The Genome EDIC CC turns the security and risk policies into minimum requirements for audit and certification DG V.1.2.

  • Rules and models are versioned inputs. Data models, metadata models, access request forms and minimum requirements will change. They can be updated without rebuilding the software, and each part of the system says which version it follows. This is how the architecture applies the principle; the governance doesn't prescribe it. See 4. Solution strategy and 8.9.
  • One source of truth for information about the system. The Genome EDIC CC is the single source of truth for all relevant information across the federated system, such as its documentation DG V.1.2. The data themselves stay federated.
  • This architecture follows the governance. It is written against version 2025-12 of the governance [DG]. When the governance changes, the traceability page shows which pages to review.

Implementation freedom​

Member Countries choose how they fit the infrastructure into their national infrastructure, as long as they meet the requirements and implement the common functions DG II.2. The governance gives national implementation as much flexibility as possible, while the system stays homogeneous for the User DG I.

  • Interfaces first. Each component is described by its function, interfaces and standards. The reference implementation is named: the GDI Starter Kit component for national nodes, or the GDI central service for the European scope [GDI Starter Kit]. A Member Country may use other tools that meet the same interfaces. See 4. Solution strategy.
  • Each country distributes the national roles. One organisation can hold several roles DG III, and countries should be as free as possible in how they share tasks DG VIII.3.3. Where one organisation holds several roles, the Member Country mitigates conflicts of interest: for example, a 1+MG NCP that checks compliance must not assess its own IT infrastructure DG V.1.4. Each Member Country records its choices in its national implementation profile. See 3.3.
  • Some choices are national by design. For example, whether data may be pooled for research DG VIII.3.4, or who reviews access requests for 1+MG cohort datasets DG VII.4.7. Who decides on pooling for 1+MG compliant datasets is still open (see below). The system must support every option the governance allows, and show Users which one applies.
  • Common minimum requirements, checked by audit or certification. The freedom ends where the common requirements start. All SPEs meet the same minimum requirements DG VIII.3.3, and national entities are audited against them by an external body, and/or work towards certification DG V.1.2 DG V.1.3.

Scalable​

Implementations and procedures should scale to large data volumes and many Users DG II.2.

  • Do centrally what every country would otherwise repeat. The Genome EDIC CC takes on tasks that are more efficient at central level DG I, such as running the central data catalogue and managing access requests.
  • One access request for all data. One request covers all data available in the Genome EDIC, with a form per type of use, and the portal catches obvious mistakes before submission DG VII.3.1.
  • Machine-readable descriptions. ELSI metadata are harmonised and machine-readable DG VI.1.1, so that discovery and checks can be automated.
  • Compute and storage that scale. SPEs should plan for high-performance computing DG VIII.3.3. For research and healthcare reuse, archiving should avoid keeping several copies of datasets derived from the same data DG VIII.8.2. During a sleeping period, data can move to cold storage, which is cheaper but slower to access DG VIII.3.1.

Homogeneous data that remains federated​

Virtual cohort​

The data should behave, as much as possible, as one single cohort DG II.2.

  • Common data models. 1+MG Working Group 3 defines the data models, ontologies (shared vocabularies) and metadata models DG II.1. The Assembly of Members adopts them, with quality labels DG VI.1.1. 1+MG Data Providers transform their data into these models DG VI.2.2. The 1+MG NCP checks that they do, before the data are made available DG VI.4.4. See 5.2.6 and 8.10.
  • One catalogue, one portal, one procedure. Users find all data in one central data catalogue DG VII.2.1 and start from the 1+MG User Portal, whatever the country or the type of dataset. For 1+MG data they apply there; for externally governed datasets the portal sends them to the dataset's own procedure DG VII.3.1.
  • Analysis across countries. SPEs should allow efficient analysis of data from several 1+MG Data Providers and Member Countries, ideally federated across the national SPEs DG VIII.3.3.
  • Fair access. Every User of the same type of use goes through the same procedure. Refusals are justified, and there is a redress procedure DG VI.4.3 DG VII.5.6.

Federated​

Personal data are held in a federated IT infrastructure. Users can only download non-personal results of analysis or aggregation DG II.2. As a rule, the data remain in the countries DG I.

  • Analysis runs in a 1+MG SPE or, where applicable, in the SPE provided by the European Commission under the EHDS DG VIII.2.2. When that applies is open (see below). No download is possible, so each Member Country provides SPEs, and they all meet the same minimum requirements DG VIII.3.3. See 5.2.3 and 6.3.2.
  • Only non-personal results leave the SPE. Users must not export personal data DG VIII.2.2. See 8.8 Output control.
  • Pooling is an exception, chosen nationally. Pooling means bringing data from several countries together in one SPE, for a time. For research, the governance lets each Member Country keep its data federated only. It may instead allow "data streaming" (which the governance doesn't define further) or temporary pooling with data from other countries, where the purpose of the research can't be achieved otherwise, or would be too complicated to implement in a federated way. The choice is recorded as ELSI metadata in the dataset descriptions, and passed to the 1+MG Data Providers, because it can matter to data subjects when they decide whether to have their data included DG VIII.3.4. An SPE that pools data from other Member Countries must be certified DG V.1.3. The governance describes this choice for research only. Who takes it for 1+MG compliant datasets is still open (see below).
  • Own data and tools come in. Users may bring their own data and software into the SPE, after a security review. This includes data from HDABs and externally governed datasets DG VIII.3.1. Linking such data with 1+MG data can make data subjects easier to identify. Users may not link records without permission DG VIII.2.2, and the SPE provider takes steps to limit the risk after linkage DG VIII.3.3. See 8.7.
  • Reproducibility without download. For research and healthcare reuse, as Users can't download personal data, the data must stay available through the Genome EDIC and its national entities, so that analyses can be run again DG VIII.8.1 DG VIII.8.2. See 6.3.7.

Where principles pull in different directions​

Some principles limit each other. The architecture handles them as follows.

  • Implementation freedom and virtual cohort. Countries choose their own tools, yet Users should see one system. Common interfaces, data models and minimum requirements keep the system the same for Users. What sits behind them is national DG I.
  • Federated, and analyses that need pooled data. Some analyses can't be done in a federated way. For research, the governance allows temporary pooling in a certified SPE, where the national choice allows it DG VIII.3.4. The system supports both, and shows Users which one applies to each dataset. Who decides for 1+MG compliant datasets is still open.
  • GDPR-compliant, and reproducibility. A data subject's right to rectification or erasure can conflict with stable, archived datasets. The governance handles this with limits the GDPR allows DG V.2.1, information to data subjects in advance DG V.2.2, and versioning DG V.2.6 DG V.2.7. See 8.9.
  • EHDS-proof, and stricter 1+MG rules. Components meet the EHDS interfaces and the stricter 1+MG requirements at the same time DG V.1.3. Some EHDS requirements are still a draft (see below).

What the principles cost​

Some principles bring work and cost for every Member Country and operator:

  • SPEs in every Member Country. As Users can't download personal data, each Member Country provides SPEs that meet the common minimum requirements DG VIII.3.3.
  • External audit or certification of every node. Each 1+MG IT infrastructure provider is audited by an external body and/or works towards certification DG V.1.3.
  • A certified SPE for pooling. A country that allows its data to be pooled for research needs a certified SPE DG V.1.3 DG VIII.3.4.
  • Data kept available for reproducibility. For research and healthcare reuse, the data must stay available so that analyses can be run again DG VIII.8.1 DG VIII.8.2.
Risk

A Member Country may find these efforts too costly, or not be ready in time, and join late or offer fewer data. See chapter 11.

Open points
  • Who decides on pooling for 1+MG compliant datasets. The recommendation lets each Member Country choose. Its justification says that for 1+MG compliant datasets the decision now rests with each 1+MG Data Holder, and that it could be taken at country level instead, to reduce complexity DG VIII.3.4. See chapter 11.
  • When 1+MG data may be processed in the SPE of the European Commission, "where applicable" DG VIII.2.2. See chapter 11.
  • Who signs the data use agreement for 1+MG compliant datasets: whether the Genome EDIC is mandated to sign on behalf of the 1+MG Data Holders DG VII.5.5. See chapter 11.
  • How 1+MG IT infrastructure providers are accredited is still to be defined DG III. See chapter 11.
  • The data and metadata models are not part of the governance: 1+MG Working Group 3 defines them, and the Assembly of Members adopts them DG II.1 DG VI.1.1. See chapter 11.
  • The HealthData@EU implementing act is still a draft [HDEU-IA draft], so the EHDS requirements for connecting to HealthData@EU may still change; the implementing act on SPE requirements (EHDS Art. 73(5)) is not published yet either. See chapter 11.
